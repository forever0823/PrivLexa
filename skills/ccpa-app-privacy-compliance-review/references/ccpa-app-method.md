# CCPA 应用审查方法

## 来源依据

本 skill 面向流媒体场景，但其合规结构可以较好泛化到应用审查，因为以下控制领域会反复出现：

- 数据收集与处理透明度
- 消费者权利实现
- 技术与安全保障
- 供应商与第三方治理
- 监测、审计与组织控制

本 skill 将该结构适配为应用及应用隐私政策审查流程。

## 提炼出的工作流

### 1. 适用性与上下文筛查

先确认该应用是否大概率受到加州消费者隐私义务约束。

需要记录：

- 是否面向加州居民
- 企业身份及门槛事实是否大概率满足
- 应用的商业模式
- 广告、分析、个性化、订阅和支付流程
- 未成年人、精确地理位置以及敏感个人信息

如果门槛事实或角色事实无法确认，不要猜测，标记为 `待确认`。

### 2. 透明度与告知审查

论文强调收集和处理披露的透明性。在应用审查中，可转化为以告知为核心的一轮检查：

- 收集了哪些类别的数据
- 数据来自哪些来源
- 用于哪些业务或商业目的
- 数据保留多久，或如何确定保留期限
- 是否披露了后续共享或 sale/share 行为

这一步通常证据最丰富，因为可以锚定在隐私政策、引导页、设置页、同意弹窗、应用商店披露和 SDK 清单上。

### 3. 消费者权利与控制审查

论文将用户权利实现作为独立工作流处理。要审查应用是否提供了可用的路径，用于：

- access 或 know 请求
- 删除请求
- 更正请求
- 退出 sale 或 share
- 在适用时限制敏感个人信息的使用或披露
- 用户作出隐私选择后的非歧视待遇

检查控制是否只是被提到，还是在实践中真的可用。

### 4. 安全与运营保障审查

论文对技术保障给予单独权重。在应用审查中，应检查相关材料是否描述或至少能够推导出：

- 合理安全控制
- 传输中和静态存储时的加密
- 访问控制和管理限制
- 事件响应和数据泄露通知准备情况
- 安全删除和保留执行机制

如果没有给出运营事实，就记录该缺口，而不是按常见做法臆造控制。

### 5. 供应商与 SDK 治理审查

论文反复强调第三方和供应商合规。对应用而言，这是核心风险区，因为分析、归因、广告、支付、崩溃监测、认证和客服 SDK 往往制造最严重的 CCPA 缺口。

检查材料是否清楚区分：

- service providers 和 contractors
- third parties
- sale 或 share 影响
- SDK 或 API 的类别与用途
- 合同或尽职调查表述

### 6. 监测与整改优先级

最后要把一次性的文案问题与系统性的控制问题分开。

按以下顺序确定整改优先级：

1. 被隐藏或不可用的权利控制
2. 与广告或跟踪相关的 sale/share 模糊表述
3. 敏感个人信息和未成年人
4. 第三方或 SDK 披露缺口
5. 缺失的保留、安全或泄露响应细节
6. 过时政策、缺少审计日志或治理薄弱

## 面向应用的适配规则

把论文中的流媒体示例翻译成通用应用语言：

- viewing history -> 使用日志、事件历史、交互历史
- recommendation engine -> 个性化、排序或画像逻辑
- subscriptions and billing -> 支付、购买和账户数据
- cookies and trackers -> 移动 SDK 标识符、设备 ID、广告 ID、像素和应用内跟踪
- vendor compliance -> 分析、广告技术、支付、认证、崩溃监测、消息推送和客服提供方

## 当前校准说明

使用论文工作流，但将实际审查校准到 2026 年 3 月 12 日时点的加州现行规则：

- 以经 CPRA 修订后的 CCPA 为基线
- 纳入更正权、敏感个人信息控制以及 “Do Not Sell or Share” 分析
- 将 Global Privacy Control 及其他退出偏好信号视为实时审查项
- 对退出类请求不要求身份验证
- 严格检查界面是否存在暗黑模式摩擦
- 将 16 岁以下未成年人作为更高严重性分支

## 高风险模式

当出现以下模式时，应提升为 `高风险` 或 `待确认`：

- 一边写着 “we do not sell”，一边又使用广告技术或跟踪 SDK，且没有解释
- 只给出一个权利邮箱地址，却没有清晰流程、数据类别或响应预期
- 没有 collection notice 或没有保留期限披露
- 集成了多个 SDK，却完全不提第三方类别
- 退出控制被藏在登录墙后或需要多步摩擦操作
- 没有区分 contractor/service-provider 传输与 third-party 披露
- 涉及未成年人或精确地理位置处理，但控制措施描述模糊笼统
